# 音频路由与插件插入拓扑

> 状态：**讨论稿（v1 定稿部分 + 待验证部分已标注）**
> 范围：给「效果器链」找插入点、定义分轨（stems）的混音位置、定 PDC 规则。
> 与实验台文档的关系：`junk_fusion_plugin_lab/docs/host-integration.md` 讲**插件怎么安全加载**，
> 本文讲**加载完插在这条路由的哪里**。两边结论冲突时以实验台为准（那是实测）。
>
> 读者：主项目实现者（包括我自己）。

---

## 0. 一句话

音频路由是**三层总线树**，不是一条链：

```
分轨(stem) → [stem 效果链] → 分轨混音 → [歌曲总线效果链] → 交叉淡化 → [全局效果链] → EQ → 主音量 → 淡入淡出 → 输出
```

三个插入层的**归属不同**，所以位置不同：stem 链和歌曲总线链是"这首歌的"，全局链是"这个应用的"。

---

## 1. 现状（已实现，作为基线）

```
            ┌──────────── Deck 0（每首歌独占一条）─────────────┐
[解码线程0] → │ AudioRingBuffer → speedShifterBuffer → Stretch │ → deckOut0
            └────────────────────────────────────────────────┘
            ┌──────────── Deck 1 ────────────────────────────┐
[解码线程1] → │ AudioRingBuffer → speedShifterBuffer → Stretch │ → deckOut1
            └────────────────────────────────────────────────┘

deckOut0 ─┐
          ├─→ CrossFadeArea ─→ Eq ─→ 主音量(逐样本) ─→ PlayPauseControl
deckOut1 ─┘                                              ─→ PlayCount ─→ ProgressBar
                                                         ─→ SpectrumAnalyzer → 声卡
```

事实清单（写设计前必须记住的）：

| 项 | 值 |
|---|---|
| 块大小 | Debug 实测 **441**（44.1kHz / 10ms）；插件 `prepareToPlay` 的 maxBlock 要按"最大可能"给 |
| 交叉淡化 | 切歌 600ms，seek 50ms；**两个 deck 同时出声**是常态 |
| 变速变调 | `Stretch` 在 deck **最末端**，输入 `n × 速度比`，输出 `n` |
| deck 内暂停 | `isFullMute` 直接把 deck 输出清零（不淡出） |
| EQ 位置 | 交叉淡化**之后**、主音量之前 |
| 频谱 | 取最终输出（EQ + 主音量之后） |

## 2. 三个插入层

| 层 | 归属 | 实例数 | 插入点 | 块大小 | 需要 PDC |
|---|---|---|---|---|---|
| **stem 链**（分轨效果） | 这首歌 | 每 stem × 2 deck | 解码之后、分轨混音之前 | 固定 n（建议） | **要**（stem 之间对齐） |
| **歌曲总线链**（单曲效果） | 这首歌 | 2（两个 deck 各一份） | Stretch 之后、交叉淡化之前 | 固定 n | 不要（deck 内单链） |
| **全局链**（应用效果） | 应用 | 1 | 交叉淡化之后、EQ 之前 | 固定 n | **不要**（单链） |

命名建议（前后端/文档统一，别混用）：

- `stemChain` / `trackChain` —— 分轨
- `songBusChain` —— 歌曲总线
- `masterChain` / `globalChain` —— 全局

## 3. 目标拓扑

### 3.1 无分轨（v1 / v1.5，先做这个）

```
Deck 0: 解码 → 环形缓冲 → Stretch → [歌曲总线链 A] ─┐
Deck 1: 解码 → 环形缓冲 → Stretch → [歌曲总线链 B] ─┼→ CrossFade
                                                    │
CrossFade → [全局链] → Eq → 主音量 → PlayPause → PlayCount → Progress → Spectrum → 声卡
```

v1 只做**全局链**，先把 `[歌曲总线链]` 留空（旁通），拓扑不变。

### 3.2 有分轨（v3，暂缓）

```
Deck N（每首歌一条）:
  ┌ stem0: 解码 ─→ [stem0 链] ─→ 延迟(Lmax-L0) ─┐
  ├ stem1: 解码 ─→ [stem1 链] ─→ 延迟(Lmax-L1) ─┼→ 分轨混音 → speedBuf → Stretch → [歌曲总线链]
  └ ...                                        ─┘                                  │
                                                            deck 输出 ←────────────┘
Deck0/Deck1 → CrossFade → [全局链] → Eq → 主音量 → ...
```

**关键点：Stretch 在分轨混音之后（单实例）。** 理由见 §5。

## 4. 为什么插在这些位置（决策记录）

### 4.1 全局链必须在交叉淡化**之后**

1. 它的语义是"跨歌曲共享一份状态"。放在 deck 里 = 两个实例 = 两份状态
   （混响尾巴、压缩器包络、调制相位各不相同），切歌时状态会跳。
2. 单链 → **不需要 PDC**（`host-integration.md` §3 的结论）。
3. 交叉淡化的是"干声"，全局链看到的是一段连续的、包含淡化曲线的信号；
   限幅器/压缩器不会被两次交叉淡化各触发一遍。

### 4.2 歌曲总线链必须在交叉淡化**之前**（两个 deck 各一份）

1. 600ms 交叉淡化期间**两首歌同时出声**。若放在交叉淡化之后，两条歌只能共用一条链：
   上一首的混响尾巴会被下一首的混响参数处理，且**根本无法做到"每首歌一套效果器"**。
2. 歌曲专属的效果尾巴应当跟着那首歌一起淡出，这才是听感正确的。
3. 代价：两个 deck = 两个实例。只在交叉淡化期间同时活跃；平时不活跃的 deck 可以整链旁通。

### 4.3 必须在 `Stretch` **之后**

1. 插件面对的是"最终播放速率"的信号：块大小固定 = n，采样率不变，延迟值可解释。
2. 若在 `Stretch` 之前：块大小随速度比变化（`n × ratio`），插件要适应每块不同的
   `numSamples`（合法但少见，老插件容易翻车）；而且插件的延迟会被拉伸比缩放，
   PDC 从"常数"变成"随 ratio 变化的数"。
3. 例外：**分轨时** stem 链必须早于"单实例 Stretch"（因为要先混），见 §5。

### 4.4 与 EQ 的先后

`[全局链] → Eq`：EQ 是用户最后的"总音色修正"，要能修插件造成的问题（比如磁带模拟
太亮）。反过来"EQ 进失真"是吉他音箱的用法，不是播放器的需求。

### 4.5 与主音量 / 暂停淡出的先后

`Eq → 主音量 → PlayPause`：暂停时整条链的尾巴都要被淡掉。如果把插件放在
PlayPause 之后，暂停后混响还会响——那不是播放器该有的行为。

## 5. 分轨（stems）方案

### 5.1 前置契约（离线分轨必须保证，否则后面全白搭）

1. 所有 stem 与原始音频**等长、同采样率、同声道数**，且第 0 个采样点对齐；
2. 每个 stem 单独可解码，格式建议统一（WAV/FLAC 均可，但不要一个 MP3 一个 FLAC）；
3. 离线分轨是**一次性**产物，播放时不再合成——所以 stem 的数量与体积要落库/落文件系统记得住。

### 5.2 解码：单线程锁步，不要 N 个解码线程

每个 stem 一条 `FFmpegDecoder` 线程会导致 seek 不同步、边界漂移。
建议：**一个"分轨组"解码线程，循环里对每个 stem 读同样多的样本**，
写进各自的环形缓冲（或一条 N 声道的大环形缓冲）。锁步是结构保证，不靠运气。

### 5.3 Stretch 必须放在分轨混音之后（单实例）

`Stretch` 是有状态的自适应算法：同样的输入长度，不同内容的内部决策不同。
**每个 stem 各 stretch 一次，样本数还是对齐的，但相位/瞬态会互相错开**，
表现为鼓变糊、整体发虚——这不是 PDC 能修的（PDC 修常数延迟，修不了频变/时变漂移）。

所以：stem → [stem 链] → 混音 → **单实例 Stretch** → deck 输出。

代价（必须承认）：stem 链处理的是**变速前**的信号，插件的混响/延迟尾巴会跟着
播放速度一起被拉伸（像磁带变速）。对"降速练听"这种场景，这符合直觉。

> 备选方案 S2（暂不采用）：每个 stem 各 stretch 一次，stem 链放到 stretch 之后。
> 优点是插件块大小/速率稳定、混响不会被拉伸；缺点是 §5.3 的相位问题，
> 且 stem 数 × stretch 的 CPU。只有在实测证明相位问题可接受时才考虑。

### 5.4 分轨模式下的变速

S1 方案下变速仍然可用（单实例 stretch，在混音之后）。但要注意：

- 插件延迟按"变速前样本数"计，最终输出延迟 = L / ratio（要显示给用户的数字要用输出样本）；
- stem 之间的对齐在变速前完成即可，变速对它们一视同仁，不会破坏对齐。

## 6. 延迟与 PDC

### 6.1 三层各自的规则

| 层 | 需要补偿吗 | 怎么补 |
|---|---|---|
| 全局链 | **不用** | 单路径，只是整体延迟预算；超过 ~20ms 要在进度条上提示/补偿 |
| 歌曲总线链 | **不用** | deck 内单路径；但会影响"显示进度 vs 听到进度"的差值 |
| stem 链 | **必须** | 每 stem 延迟 `Lmax - Li`，Lmax = 所有 stem 链延迟的最大值 |

### 6.2 延迟必须重读的时刻（来自实验台）

1. `prepareToPlay` 之后（TDR Nova：prepare 前 0，后 184）；
2. **第一个 block 之后**（有的插件第一块才给真值）；
3. 参数变化之后（CHOWTapeModel 运行中 39 → 43）；
4. 采样率 / 块大小变化之后。

### 6.3 实现要点

- 每个 stem 一条**环形延迟线**（容量按 `maxLatencySamples` 预分配，比如 8192）；
- 延迟量变化时不能直接跳（会爆音）：要么做 `~5ms` 的交叉淡化，要么只在
  "停播/切歌"这种本来就静音的时机应用；
- **旁通 = 硬切**（实验台结论），但旁通会改变该 stem 的延迟 → 必须在**同一块**里
  重算 PDC，否则对齐会瞬间错开；
- 延迟是"常数 + 可能变化"，所以要有一个 `pdSamples` 的原子量给 UI 看（进度条补偿用）。

### 6.4 不要做的事

- 不要用脉冲测量值驱动运行时对齐（实验台 §3：只信 `getLatencySamples()`）；
- 不要假设"报 0 就是 0"（ChowMatrix/Gateway 报 0 且实测 0 是巧合，不是规律）；
- 不要为全局链做 PDC（没有第二条路径，补了只会让播放和显示更错）。

## 7. 插件生命周期

### 7.1 实例数

| 场景 | 实例数 |
|---|---|
| 全局链 | 1 套 |
| 歌曲总线链 | 最多 2 套（两个 deck 各一份） |
| stem 链 | 每个 stem × 每个 deck（分轨最贵的地方） |

### 7.2 增删插件（不能在音频线程做）

1. UI → Coordinator → 音频进程；
2. 音频进程在**非实时线程**上构建新链（实例化插件、`prepareToPlay`、读延迟）；
3. 构建完成后把**指针原子换掉**，旧链挪到后台销毁（销毁可能挂死 → 超时 + 泄漏，不许卡音频线程）；
4. 换链那一块会出现"新旧并存"的瞬间：建议在新链第一块输出上做 ~10ms 淡入，避免爆音。

### 7.3 崩溃 / 挂死

沿用 `host-integration.md`：preflight 在临时子进程里跑、黑名单计数、白名单强制。
**PDC 也必须在 preflight 报告里带上延迟值**，否则插入后要等几十毫秒才知道对齐量。

## 8. 已知风险 / 待验证

| # | 风险 | 现状 | 怎么验证 |
|---|---|---|---|
| 1 | 块大小 441 与探针的 512 不同，延迟值可能不同 | 🟡 | 主项目实测：同一插件在 441 下读两次延迟 |
| 2 | 插件链在音频线程上跑（标准 DAW 做法），一个坏插件 = 一次 glitch | 已知 | 黑名单 + 链长上限 + UI 一键旁通整链 |
| 3 | 分轨 + 变速的相位问题（S1 已规避，S2 未验证） | 🟡 | 只有到 v3 才需要 |
| 4 | 切歌时旧链销毁可能挂死 | 已知 | 超时 + 后台销毁 |
| 5 | 链很长时总延迟（3 × 184 ≈ 552 样本 ≈ 12.5ms） | 设计约束 | 链长上限 8，UI 显示总延迟 |
| 6 | 交叉淡化期间两个 deck 各跑一套链，CPU × 2 | 设计约束 | 只在实际启用交叉淡化时才需要两套 |

## 9. 落地顺序

1. **全局链（v1）**：`CrossFade → [全局链] → Eq`。无 PDC、单实例、块大小固定。
   前端效果器页就是它。
2. **歌曲总线链（v1.5）**：deck 内 `Stretch` 之后加一条链，两个 deck 各一份；
   换歌时构建/销毁的流程同 §7.2。
3. **分轨（v3）**：先定离线分轨的产物契约（§5.1），再做锁步解码（§5.2）、
   单实例 Stretch（§5.3）、stem 链与 PDC（§6）。
4. 每一步都补一条"链路自检"：旁通时 `rmsDiff == 0`，启用时 `diffToSignal > 0`
   （实验台实验 8 的指标可以直接搬到主项目当回归测试）。
